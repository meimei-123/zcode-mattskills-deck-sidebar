# setup-home-repo

把 home-repo 文档里给人读的项目指针，落成看板能读的项目清单 `.deck/projects.json`。做法是读文档、列候选表、等用户确认、写清单、再验证。清单已经在时改做对账，只动用户选中的差异。

这是一段带人确认的流程，不是无人值守的脚本：**候选表经用户明确确认后才写盘**，用户点头之前不写任何文件。

home-repo 指本次会话的工作区根。清单入口发来的消息里带了路径就用它，没带就用当前工作目录。

## 流程

开头先调一次 `deck_project_list`，按回包里 `registry.status` 分两条路，两条路都从探索走起：

| 清单现状                      | 走哪几节                              |
| ----------------------------- | ------------------------------------- |
| `missing`（还没有清单文件）   | 1 探索 → 2 呈现与确认 → 4 写入 → 5 收尾 |
| `ok` 或 `broken`（清单已在）  | 1 探索 → 3 对账 → 4 写入 → 5 收尾      |

清单入口发来的消息里说的现状只是发出时的快照，以这次调用的回包为准。

## 1 探索

### 读哪些文档

按这个顺序读 home-repo 根下的文档，没有的跳过：

1. `AGENTS.md`
2. `CLAUDE.md`
3. `README.md`

它们点名当导航用的文档（项目地图、目录索引一类）接着读。不通读整个仓库。

### 哪些算项目指针

四种形态都算，逐行找：

- 表格里的路径列（一行一个项目）
- 列表项里的路径
- 指向本地路径的链接
- 行内代码里的路径

路径写法认绝对路径（带盘符、UNC、POSIX 三种写法都算），也认 `~/`、`../`、`./` 开头的相对写法。

### 不收什么

- 解析后落在 home-repo 内部的路径，home-repo 自己也算在内。
- 命令示例里的路径。
- 输出目录：构建产物、依赖、缓存、日志这些。

### 逐个核实

相对路径按 home-repo 根解析，`~/` 按用户主目录解析，然后取真实路径。目录存在、真实路径又不是 home-repo（也不在它里面）的，才是候选。

目录里有没有 `.git`、`.scratch`、`AGENTS.md` 只记下来当佐证，不作收录条件：文档点到了就收，哪怕它眼下还没有看板。

目录不存在的指针不进候选表。表下面单列一行告诉用户「文档里有、目录不在」，目录搬了家就由用户给新位置。

同一个目录在几处出现只列一行，出处记最先读到的那处。

### 一个候选都没有时

文档里抽不到指针，或者抽到的目录都不存在，就列出 home-repo 父目录下的一层兄弟目录作候选，不往下递归。按目录名排，带 `.scratch` 的排前面。

## 2 呈现与确认

给一张候选表，每行一个项目：

| #   | 建议短名 | 路径              | 出处                    | 佐证                   |
| --- | -------- | ----------------- | ----------------------- | ---------------------- |
| 1   | `alpha`  | `../alpha`        | `AGENTS.md` 第 12 行    | 有 `.scratch`、`.git`  |
| 2   | `beta`   | `/srv/work/beta`  | `README.md`「项目」一节 | 无                     |

- 建议短名默认取目录名。跟 home-repo 的目录名重名，或者跟别的候选重名（不区分大小写）时，另给一个不重名的建议，并在表里标出来。
- 路径：候选和 home-repo 同一个父目录时写 `../<目录名>`，其余写绝对路径。
- 出处写到文件和行号。
- 佐证写目录里实际看到的 `.scratch`、`.git`、`AGENTS.md`，都没有就写「无」。

表下再单列探索时发现的「文档里有、目录不在」的指针。然后请用户删行、补行、改短名；路径写法想换（相对改绝对，或反过来）也照改。用户补的行先照第 1 节核实再入表。

home-repo 有 `AGENTS.md`、里面又有项目地图时，顺带问一句：要不要在项目地图下加一行指向清单的指针。用户说要，写清单时一并加这一行；没说就什么文档都不动。

**停在这里，等用户明确确认。** 明确确认是用户对这张表说了「可以」「就这样」或意思相同的话，改完行之后的确认也算。用户没回、回得含糊、或者说「你看着办」，都不算，接着问。表是空的（连兄弟目录都没有）就如实报告，不写盘，到此为止。

## 3 对账

清单文件已经在时走这一节，不整份覆盖。先照第 1 节探索，再和清单逐条比。两边都取真实路径，按真实路径对上号，差异分三类列给用户：

1. 文档有、清单没有：建议新增，给出建议短名。
2. 清单有、文档没有：项目可能已经下线，也可能只是文档漏写，保留还是移除由用户定。
3. 两边都有但不一致：短名不同，或者同一个短名在两边指向不同目录。以哪边为准由用户定。

`warnings` 里被跳过的条目也逐条列出，附上原因和改法（路径写错、重名、和别的条目指向同一个目录、写成了 home-repo 自己）。

清单与文档完全一致、也没有 warning 时，报告「无需改动」，不写盘，到此为止。

清单损坏（`broken`）时工具读不出条目。把 `registry.error` 原样告诉用户，直接读原文件，把还认得出来的条目（name 和 path 都读得出的）当候选带进表里，然后照第 2 节给一张完整的候选表。这次写入会整份替换那个坏文件，所以表要让用户看全。

差异和候选列出来之后同样停下，等用户逐项选定，再进入写入。

## 4 写入

写 home-repo 根下的 `.deck/projects.json`。`.deck/` 不存在就建，文件用 UTF-8，不带 BOM：

```json
{
  "version": 1,
  "projects": [
    { "name": "alpha", "path": "../alpha" },
    { "name": "beta", "path": "/srv/work/beta" }
  ]
}
```

home-repo 自己不写进文件，它永远隐式存在、排第一。表里的短名进 `name`，路径进 `path`。

条目规则和清单校验是同一口径，违反的条目会被跳过并报 warning：

- `path` 必填。写绝对路径，或者相对 home-repo 根的相对路径（不是相对 `.deck/`）。`~` 和环境变量不展开，也不支持通配符。
- 目录必须存在，并且是目录。
- `name` 非空，不含 `/` 或 `\`。
- `name` 不区分大小写唯一，也不能和 home-repo 的目录名相同，这个名字留给 home-repo。
- 不写 `"."`，也不写 home-repo 自己的真实路径。
- 两条指向同一个目录时（junction、符号链接指到同一处也算），只有排在前面的那条生效。
- JSON 字符串里的反斜杠要写成两个 `\\`。Windows 绝对路径也可以直接用 `/` 分隔，省去转义。

对账之后写盘只改用户选中的条目（清单损坏时写的是第 3 节那张让用户看全的表），其余条目的短名、路径写法和先后顺序原样保留。

不要替用户 `git add` 或提交清单。

## 5 收尾

1. 调 `deck_project_list` 验证，三项都对才算完成：`projects` 第一项是 home-repo（`isHome` 为 `true`）；确认过的项目都在，且 `valid` 为 `true`；`warnings` 是空数组。`warnings` 不空，就照每条警告说的原因改清单再调一次，直到为空。改不动就如实报告卡在哪一条。
2. 默认不改 `AGENTS.md` 和 `.gitignore`。`AGENTS.md` 只在第 2 节用户答应了那行指针时动，且只加那一行；`.gitignore` 不动。
3. 报告写了哪些条目、验证结果如何，并提醒一句：清单里有本机绝对路径时，这个文件不适合提交进版本库；全是 `../` 相对路径的才可以。入不入库由用户决定。

清单落盘后面板会在下一次刷新时出现项目 chip，不用重开会话。
